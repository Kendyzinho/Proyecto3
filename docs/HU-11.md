# HU-11 — Registro manual excepcional

Implementación sobre `feature/hu-11-registro-excepcional`. Reutiliza Sanctum, autorización de roles, habilitaciones de HU-07, relaciones de prácticas de HU-10 y el layout Marco.

## API

Todas las rutas requieren un token Sanctum y `rol:coordinadora`. No se ampliaron permisos de nómina.

| Método y ruta | Contrato |
|---|---|
| GET `/api/coordinacion/metricas` | `{ periodo: { id, nombre } \| null, practicas_registradas: number }`. Cuenta prácticas del período actual, incluyendo futuras. |
| GET `/api/coordinacion/practicas-excepcionales/catalogo?periodo_id=ID` | `{ periodo: { id, nombre }, habilitaciones: [{ id, estudiante, tipo_practica }], supervisores: [{ id, nombre, centro }] }`. El ID seleccionable es el de la habilitación. |
| POST `/api/coordinacion/practicas-excepcionales` | Recibe los campos indicados abajo. Retorna HTTP 201 y `{ data: { id, origen, registrada_por, created_at } }`. |

```json
{
  "periodo_id": 2,
  "habilitacion_id": 7,
  "supervisor_id": 3,
  "modalidad": "presencial",
  "fecha_inicio": "2026-11-01",
  "fecha_fin": "2026-12-01",
  "justificacion_excepcional": "Regularización autorizada por Jefatura."
}
```

Los IDs del ejemplo son ilustrativos: obtenerlos del catálogo real. Errores: 401 sin sesión, 403 sin rol, 422 con `errors` por campo. El backend prohíbe `centro_id`, `origen` y `registrada_por` en la petición. La autoría procede de la sesión, el origen siempre es `excepcional` y el centro procede del supervisor.

## Persistencia

Migración aditiva: `2026_10_18_180000_add_registro_excepcional_to_practicas.php`. Añade `justificacion_excepcional` (text nullable) y `registrada_por` (FK nullable a users). Las prácticas ordinarias siguen siendo compatibles. `created_at` conserva fecha y hora. `Practica::autoraRegistro()` permite consultar la autora.

La migración se prueba solo en `practicas_test`. **No aplicar en proyecto3_integrado sin aprobación explícita.** No editar migraciones históricas ni ejecutar migrate:fresh en desarrollo.

## Reglas y límites

- La habilitación debe cumplir prerrequisito, pertenecer al período solicitado y corresponder a un usuario sin baja.
- Cualquier práctica previa bloquea otra para esa habilitación. No hay estados fiables para permitir reemplazos, cancelaciones o reintentos académicos.
- La transacción bloquea la habilitación con `lockForUpdate` antes de revisar duplicidad, además del supervisor y centro. Los futuros creadores de HU-08/HU-09 deben adoptar el mismo protocolo; no hay un índice único global nuevo que altere sus reglas.
- El supervisor y centro no pueden estar dados de baja. Se reutiliza `puedeRecibirEstudiantes()`: centro interno o acuerdo vigente. La vigencia se evalúa al registrar, conforme a HU-10.
- Modalidades: presencial, a_distancia, mixta. Fechas ISO obligatorias, término igual o posterior al inicio. No se imponen límites de calendario no acordados. El período se deriva de la habilitación, no de las fechas.
- Justificación no vacía ni formada por espacios, hasta 5000 caracteres.
- Cupos no bloqueantes: la interfaz indica disponibilidad no determinada. Acordar reglas con HU-08/HU-12.
- El inicio usa el período actual. La API admite un período existente coherente con su habilitación, pero HU-11 no añade un selector histórico al inicio.
- La métrica cuenta todas las prácticas registradas del período, no actividad por fechas. Después del registro se consulta nuevamente el backend; un fallo de recarga muestra un error y permite reintentar.
- El aviso del diálogo informa de la marca persistida. La ficha completa de estudiante/práctica queda para su historia correspondiente.

## Interfaz

Inicio mínimo con encabezado, botón y tarjeta. Diálogo Material con selectores reales, centro de solo lectura, ambas fechas, modalidad y justificación. Incluye carga, error, ausencia de candidatos, validación del servidor, bloqueo de doble envío, cancelar y confirmación. El cierre se bloquea durante el envío. Marco admite una opción `adaptable` activada solo por Coordinadora para menú superpuesto en móviles. Mantiene Inter, azul #355085, dorado #edb01c y fondo #f1f5f9 del tema existente.

## Prueba manual pendiente de aprobación de desarrollo

1. Aprobar la migración aditiva y, si se desea un caso positivo, el seeder optativo descrito abajo.

3. Iniciar backend y frontend con la configuración habitual; entrar como Coordinadora y abrir `/coordinacion`.
4. Comprobar el total real y abrir “Nueva práctica”. Sin seeder adicional, los cinco estudiantes existentes ya tienen práctica y se muestra el estado vacío.

6. Cancelar debe conservar el total. Registrar debe cerrar el diálogo, confirmar el éxito y aumentar el total sin recargar la página. El candidato desaparece al abrir de nuevo.
7. Verificar que HU-10 liste la nueva práctica para el mismo período.
8. Revisar el diálogo en móvil, navegación con Tab, Escape antes del envío, etiquetas y errores. Durante envío no debe permitirse otro registro ni cierre.

## Verificación automatizada

Laravel: ejecutar `php artisan test` desde backend, con `phpunit.xml` y el guard `BaseDeDatosAislada` que verifica `SELECT DATABASE()` antes de refrescar exclusivamente `practicas_test`. La prueba concurrente inicia dos procesos PHP y dos peticiones HTTP Kernel con el mismo token/habilitación; exige una respuesta 201, otra 422 y una sola fila. Sus fixtures se confirman únicamente en pruebas para que ambos procesos puedan verlos y se marca la base para reconstrucción en el siguiente test.

Angular: `npm test -- --watch=false`. Incluye tests de formulario, errores, carga, vacío, doble envío, cancelación, centro, recarga de métrica y regresiones de autenticación/perfil. Producción: `npm run build`. En Windows puede ser necesario `CI=true` y `NG_BUILD_MAX_WORKERS=2`; el tema existente descarga Google Fonts durante la compilación.
